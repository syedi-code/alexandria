# Running the works migration

`sql/migrations/0026_works.sql` renames `books` to `works`, `authors` to
`creators` and `book_media` to `work_media`, and moves each work's PDF onto a
new `documents` row. It is the only irreversible step in the alexandria / stylus
/ scribe split.

The API it feeds is unchanged. `GET /books`, `GET /books/library` and
`GET /books/:id/detail` return exactly the payload they returned before — the
characterisation snapshots in `packages/core/test` are the proof, and they are
generated by running the fixture through this migration.

## Order matters

The schema change and the code deploy are not independent. Once 0026 has run
there is no `books` table, and the currently deployed worker reads one. Once the
new worker is deployed it reads `works`, which does not exist until 0026 has
run. Either order leaves a window of 500s, so keep it short: run the migration,
then deploy immediately.

There is no safe way to widen that window without a dual-read shim, which is not
worth building for a single-tenant app. Pick a quiet minute.

## The sequence

```bash
# 1. Back up. D1 Time Travel gives 30-day point-in-time restore on top of this,
#    but an explicit dump is cheap and does not depend on Cloudflare.
npm run backup:prod

# 2. Record the citations that resolve today. Note the numbers.
npm run verify:tokens:prod

# 3. Rehearse on staging first, all the way through step 6.
npm run sql:staging -- 0026_works.sql
npm run verify:tokens:staging
npm run deploy:staging

# 4. Apply to production.
npm run sql:production -- 0026_works.sql

# 5. Every [[book:UUID]] token in every essay must still resolve, and the
#    counts must match what step 2 printed. This is the check that matters
#    most: work ids live inside essay prose, so a remapped id corrupts an
#    essay silently, with nothing failing at write time.
npm run verify:tokens:prod

# 6. Confirm the schema is ahead of the code, then deploy.
npm run assert:migrated:prod
npm run deploy:prod
```

CI runs step 6's check too, on every push to `main`, and refuses to deploy if
production still has `books`. That is a backstop, not a substitute for doing
these in order.

## If step 5 reports broken citations

Stop. Do not deploy. Restore and work out why:

```bash
npx wrangler d1 time-travel restore antisocial-media --timestamp <ISO8601>
```

A broken citation after this migration would mean a work id changed, which 0026
never does — it renames tables rather than copying rows precisely so that ids
cannot move. Investigate before retrying.

## What to expect afterwards

- `books`, `authors` and `book_media` are gone. `works`, `creators`,
  `work_media`, `documents`, `transcriptions` and `pages` are there instead.
- `notes.book_id`, `quotes.book_id` and `essay_references.entity_id` keep their
  names and their values. SQLite rewrote their `REFERENCES` clauses to point at
  `works` when the table was renamed; nothing in writing/ was touched.
- `works.pdf_url` and `works.pdf_page_offset` are gone. They live on
  `documents.r2_key` and `documents.page_offset`, and reach the API through
  `works.primary_document_id`.
- `DELETE /books/:id` now soft-deletes by setting `works.deleted_at`. The work
  disappears from listings and still resolves by id, because essays cite it.

## Verifying by hand

```bash
npm run sql:production -- --command "SELECT COUNT(*) FROM works"
npm run sql:production -- --command "SELECT COUNT(*) FROM documents"
npm run sql:production -- --command "PRAGMA foreign_key_check"
```

`documents` should hold one row per work that had a `pdf_url`, and
`foreign_key_check` should return nothing.
